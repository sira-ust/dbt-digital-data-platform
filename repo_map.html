fct_social_mentions

Only the genuine, real food posts — spam and off-topic noise filtered out.

How: LEFT JOIN box #1 to box #2, add conformed dimensions (posted_week + market from the tracker; split followers_or_rank into follower_count vs domain_rank), then filter — keep food-relevant rows and drop spam only when the model is confident, so a shaky spam call can't hide a real mention:

int_social_concept_trends the gate

Ranks what's trending each calendar week — dishes and stockable items on two separate boards.

How: two streams, ranked separately so viral dishes can't crowd out items — unnest(mentioned_dishes) → class dish, and unnest(mentioned_products) → class item (sellable goods a grocery or restaurant could order — the product/commodity call is made by the enrichment prompt, not by a filter here; seed_social_generic_terms is only a backstop). strip_parenthetical_gloss() + fold_concept() fold language/spelling variants (bánh khọt → banh khot) to one key. Then aggregate per calendar week (Monday-anchored) → score → row_number() per (week, class). One week in, one week out: week-over-week movement compares equal, non-overlapping periods, which is what rank_change and is_rising read. mention_share (a concept's share of that week's mentions) is the measure that survives a partial week or a change in collection volume — raw counts do not. Materialized as a table because it's the gate the resolver reads.

trend_score = distinct_authors × (1 + ln(1+engagement_norm)/5 + ln(1+views_norm)/10) × single_channel_dampener

stg_mentionlytics__concept_resolution

The AI's answer for each trending concept: do we sell it, or something close?

How: view exposing concept_norm → matched_prtnum, recommended_prtnums, match_confidence. Cast + dedupe (latest resolved_at wins per concept — the source is append-only).

offline LLM resolve_trending_concepts.py MODEL_SERVING
Takes this week's top 20 of each class (dishes and items) from box #4, plus real example posts from box #3 and our product catalog, and asks the AI: do we sell this, or something close? The AI checks stock first — if we carry the item directly, that wins, even for a whole dish. Then a SECOND, independent pass reviews every candidate against its real catalog name and throws out what it can't defend, and only the survivors are saved — so the board can't show a confident-looking wrong match. Answers are checked against the real catalog too, so they can never point to a product that doesn't exist. This step runs outside dbt — it reads dbt tables and writes back a new one dbt picks up right here.

mart_social_trending_items the board

The finished weekly report: what's trending this week, whether it climbed since last week, do we stock it, what to do about it.

How: trends ⋈ resolution ⋈ int_jdawms_items_active (authoritative name) ⋈ current stock (latest snapshot week). One row per (calendar week, class, concept): where is_top_n and week_start = max(week_start) is this week's board, the other weeks are the trajectory behind it (kept in full for any concept that ever reached the top 20, so charted lines have no holes). A confidence floor social_resolve_min_confidence (0.7) suppresses any match below it (a 0.45 sushi→corn-oil guess is dropped, not shown) — and since resolver v5 that floor gates a verified confidence, not the proposing model's self-rating. recommended_prtnums are re-verified against the active item master (hallucinated SKUs, discontinued items and duplicate names dropped). Emits action_signal:

promote_now · carried & in stock restock · carried, no stock offer_substitute promote_ingredients · basket source_new · none monitor

Data quality — dq_* models

Distinct from the YAML / singular gate tests that block a build (PK, not-null, accepted-values, relationships). These dq_* models run every build but never block it — queryable bad-row / drift tables. Decision rule: blocks the pipeline → a test; ongoing drift to monitor or quarantine → a dq_ model.
